How to connect to the Parent CA

During initial setup, the parent CA uses a self-signed certificate. Both HTTPS and HTTP are supported:

HTTPS (recommended) — https://<ip-or-hostname>:8443
SSL certificate validation is automatically skipped during setup to allow connecting to a parent CA that only has a self-signed web server certificate. This is normal and expected during CA bootstrap.
HTTP (alternative) — http://<ip-or-hostname>:8080
The parent CA exposes health, status, signing, and chain endpoints over HTTP on port 8080. Use this if HTTPS connectivity is problematic. Note: CA private keys are never transmitted over this connection — only the CSR and signed certificate.
DNS vs IP address
Using a DNS hostname is preferred if available, as it makes the topology easier to manage if IPs change. However, IP addresses work fine. Always include the port number (8443 for HTTPS, 8080 for HTTP).
Tip: Make sure the parent CA has completed its own setup before connecting. The parent must be fully initialized with its root certificate generated.

PKI Distribution URLs Explained

When a CA signs a certificate, it embeds URLs that tell clients where to find revocation data and the CA's own certificate. These URLs must be publicly accessible to any machine that needs to validate your certificates.

CRL Distribution Point (CDP) All CA Roles

The CDP URL points to a file containing the Certificate Revocation List -- a signed list of all revoked certificate serial numbers. Clients download this file periodically to check whether a certificate has been revoked.

Target: Every CA tier that revokes certificates needs its own CDP. In practice, the Issuing CA is the one revoking end-entity certificates most often, but Root and Intermediate CAs also publish CRLs for subordinate CA revocation.

Root CA:         http://crl.example.com/root-ca.crl
Intermediate CA: http://crl.example.com/intermediate-ca.crl
Issuing CA:      http://crl.example.com/issuing-ca.crl

Use a dedicated hostname like crl.example.com that points to a web server or CDN serving the CRL files. Avoid port-based URLs -- they may be blocked by corporate firewalls.

Authority Information Access (AIA) All CA Roles

The AIA URL tells clients where to download the issuing CA's certificate. This allows clients to build the full certificate chain even if they only have the end-entity certificate. Without AIA, clients that don't have the intermediate CA certificate pre-installed will fail to validate the chain.

Target: Each CA tier (except Root) should have an AIA URL pointing to where its own certificate can be downloaded. The Root CA certificate is typically pre-distributed via trust stores, not AIA.

Intermediate CA: http://certs.example.com/intermediate-ca.crt
Issuing CA:      http://certs.example.com/issuing-ca.crt

Use a dedicated hostname like certs.example.com pointing to a web server or CDN that hosts the CA certificate files.

OCSP Responder Issuing CA

OCSP (Online Certificate Status Protocol) provides real-time certificate revocation checking. Instead of downloading a full CRL, clients send a single-certificate query and get an immediate signed response. OCSP is faster and more privacy-friendly than CRLs.

Target: The OCSP responder should run on (or in front of) your Issuing CA instances, since they sign end-entity certificates and maintain revocation state.

OCSP Responder:  http://ocsp.example.com

DNS & Load Balancer Configuration

Create DNS records for each service hostname:

crl.example.com    → Web server / CDN serving CRL files
certs.example.com → Web server / CDN serving CA certificates
ocsp.example.com   → OCSP responder (or load balancer)

Multiple Issuing CAs? If you have more than one Issuing CA, point ocsp.example.com to a load balancer in front of all your Issuing CA OCSP responders. Each Issuing CA can respond to queries for certificates it signed.

Why HTTP, not HTTPS? CRL and OCSP responses are cryptographically signed by the CA, so transport-layer encryption is unnecessary. Using HTTP avoids a chicken-and-egg problem where validating the HTTPS certificate would itself require OCSP/CRL access.

Standalone mode: In standalone mode, all three CA tiers run on this instance. You can use a single hostname (e.g., pki.example.com) for all URLs, since this server handles everything. The built-in endpoints /api/crl/* and /api/chain serve CRLs and certificates directly.
